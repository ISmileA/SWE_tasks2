## Базовые понятия

**Что такое LLM?** Параметрическая модель последовательностей, обученная предсказывать токены и дополнительно следовать инструкциям. У неё нет гарантии истинности ответа, долговременной памяти приложения или прав на инструменты по умолчанию.

**Что такое агент?** Программа, где модель участвует в выборе действий, получает tool observations и действует в рамках управляемого цикла. В нашей системе она выбирает retrieval plan и кандидатов; приложение проверяет границы и состояние. LLM — компонент агента, не синоним всей системы.

**Почему multi-agent?** Есть роли с разными системными инструкциями и общей передачей состояния. Планировщик отвечает за план, куратор за shortlist, валидатор за проверку. Retrieval — детерминированный tool, не фиктивная дополнительная LLM. Само число HTTP-вызовов ещё не доказывает multi-agent архитектуру; здесь есть единый граф и обратная связь.

**Что такое B?** Миллиарды параметров. Количество параметров не равно размеру GGUF, активируемым параметрам MoE, контексту или качеству. Квантование уменьшает точность хранения весов; оно не является сокращением контекстного окна.

**Контекстное окно?** Максимальный объём токенов, доступных inference при конкретной конфигурации. Контекст включает инструкции, историю, tool outputs и генерацию. Мы задаём num_ctx=4096 и ограничиваем output. Больше контекста означает дополнительные memory/compute costs; оно не гарантирует лучшее следование релевантной информации.

**Галлюцинации?** Неподтверждённые или ложные сведения, выданные моделью. В evals модели давали неверные ID/вердикты и поддались injection. Защита в нашем продукте: ограниченный каталог кандидатов, schema, строгие типы, ID/count/genre/seen/availability checks, ограниченный repair и отказ. Schema гарантирует форму, не смысл.

## Почему именно этот стек

**Как выбраны LLM?** CPU и RAM, три небольшие модели для измерения, small/strong budget routing, другая семья для проверки. Проверить реальные digest в ollama-models.json. Qwen 1.7B лучше на данном маленьком probe-наборе, но это не общий leaderboard. Gemma 1B слабый судья; deterministic validation обязательна.

**Зачем Jev-like?** Быстрый discriminative router возвращает одно из разрешённых решений и probabilities, а не свободный текст. У нас TF-IDF + LogisticRegression с sigmoid cross-validation calibration. При confidence<0.75 запрос идёт к сильной LLM. Это локальный функциональный аналог, не официальный Jev, не реализация RLCD и не надёжный security classifier. Контрольных примеров всего 15.

**Почему LangGraph?** Нужны явный state, conditional edge, ограниченная петля, termination и трассируемые роли. Рассматривались CrewAI, AutoGen, Haystack и ручная оркестрация. Результаты их экспериментального сравнения не заявлены: это архитектурное сравнение, запускался только выбранный фреймворк.

**Архитектурные паттерны?** Общий orchestrated workflow с planner/executor и critic/validator. Альтернатива: free-form group chat, supervisor с динамическим delegation, choreography через события. Первое труднее ограничить по бюджету, второе гибче, но сложнее для текущего небольшого сценария; событийная хореография полезнее в распределённых процессах. Мы сознательно выбрали фиксированный ограниченный граф.

## Память и инструменты

**Каковы три слоя?** State запроса — short-term. SQLite episodes хранит недавние успешные ID и методы 7 дней. Preferences хранит явно заданный жанр 90 дней с source и timestamp. Память нового user_id не видит запись другого пользователя. В production нужен auth: переданный user_id сам по себе не является доказательством личности.

**Как обновляется память?** Явная коррекция делает transactional upsert одного ключа, TTL удаляет устаревшее при чтении, DELETE удаляет обе persistent layers. LLM не пишет выдуманные предпочтения. Явный жанр запроса приоритетнее сохранённого; модели не следует доверять право произвольно менять чужие записи.

**Почему не RAG?** Наши изменяемые факты имеют точные ключи и владельца. Similarity retrieval не решает correction, precedence и deletion. Для большого корпуса документов RAG может быть уместен; утверждать, что он всегда плох, неверно. Graphiti/временной граф, Mem0/semantic memory, LangMem/интеграция и Letta/stateful blocks рассмотрены; их сложности не нужны для одного genre preference.

**Какие tools?** Recommender.recommend(user_id, method, k, genre). user_id берётся из запроса приложения, schema разрешает только известный method и genre, k ограничен. Нет shell, Python execution, произвольного HTTP или SQL. Добавление инструмента означает изменение доверенной программы, не просьбу модели в чате.

**Что такое skills?** Доступные агенту инструкции для повторяемой задачи. Наши три SKILL.md описывают планирование, курирование и проверку, загружаются соответствующей ролью из файлов. Наличие файла без реального включения в контекст было бы декоративным.

## Рекомендации и оценка

**Как работают методы?** Content сопоставляет жанры и train-профиль. CF использует совместные положительные оценки и shrinkage. Popularity считает train positives. Bayesian mean сглаживает train rating prior. Hybrid использует reciprocal ranks. Two-Tower обучает отдельные MLP для user и item; score — dot product, не вероятность и не прогноз rating.

**BPR и negative sampling?** Loss softplus(-(score_positive-score_negative)) повышает относительный score положительного предмета. Negative берётся из доступных к train cutoff фильмов, не просмотренных пользователем в train. Ненаблюдавшийся фильм не обязательно неинтересен — это допущение implicit learning. Не использовать test для исключения negatives: это тоже информация из будущего.

**Где разделение train/test?** Общие временные границы 70/15/15, одинаковые timestamps остаются вместе. В отличие от случайного разбиения не смешиваем поздние оценки в train. На validation выбираем learning rate и эпоху. Test используем после выбора; если он хуже baseline, так и говорим. Фильмы, выпущенные после конца train, не входят в availability и negative pool.

**Почему много cold users?** Глобальная временная граница оставляет пользователей, впервые появившихся позже train. Для них все персональные методы возвращают popularity. Это реальное ограничение сценария, а не причина спрятать этих пользователей. Поэтому метрики приводятся отдельно для 55 warm и 154 cold test users (проверить актуальный artifact).

**Метрики?** Precision@K — доля релевантного в K позициях, Recall@K — доля найденных relevant holdout items, NDCG — нормированный discounted gain, MRR — обратный ранг первого попадания, HitRate — хотя бы одно попадание. Coverage — доля доступного каталога, встречавшаяся в выдаче. Genre diversity и novelty — дополнительные proxies, не человеческая оценка интересности. Пользовательский bootstrap даёт неопределённость относительно выборки, не устраняет dataset bias.

**Оценка всей MAS?** Проверяем завершение, grounding, соблюдение constraints/памяти, tool success, repair/rejection, токены и latency. Отдельно оцениваем LLM на фиксированных задачах. Маленький набор и один seed — ограничения. LLM-as-a-judge может ошибаться и коррелировать с генератором; другая семья не делает его оракулом.

**Бизнес-эффект?** Play rate, CTR, retention, watch-through и время до выбора требуют реальных impression/watch logs и A/B. Этих данных нет; нельзя выдавать offline NDCG за рост выручки. Дизайн A/B фиксируется заранее, включая primary metric, MDE, мощность и окно.

## Изоляция и наблюдаемость

**Почему недостаточно Docker?** Контейнер сам по себе разделяет kernel; неверные mounts/capabilities дают доступ к host. Наш конкретный выбор — WSL2 как доступная Linux VM плюс Bubblewrap namespaces, read-only binds, no IP network, dropped capabilities и ulimit. WSL интегрирована с Windows и сама не security sandbox. Источники и ограничения перечислены в RESEARCH.md.

**Как LLM доступна без сети?** Gateway на UNIX socket находится вне namespace, принимает только ограниченные local inference endpoints и модели. Agent sandbox не может обращаться к произвольному хосту. HTTP proxy для браузера также вне sandbox и слушает только localhost; API внутри работает через другой UNIX socket.

**Что остаётся риском?** Общий WSL kernel, доверенные gateway/Ollama, отсутствие seccomp allowlist и cgroup memory.max. ulimit не равен строгому физическому RAM limit. Не утверждать защиту от kernel exploit или полноценную multi-tenant безопасность.

**Логи, trace, span, trajectory?** Log — отдельное событие. Span — операция с длительностью, статусом и parent. Trace связывает операции одного запроса. Trajectory — действия/инструменты/решения в порядке исполнения, не скрытые рассуждения LLM. Наш trace_id общий для role spans, usage и tool decisions.

**Что мониторится и где алерты?** Requests/success/errors, token usage, role/LLM durations, validator rejections, tool success и process RSS. Логи/алерты в runtime/sandbox/observability, /metrics даёт Prometheus text. Ошибки, rejection и latency>120s пишут alert file. monitor.py может периодически вызывать health/RecSys и агентный probe. Нет настроенного email/Telegram receiver; это явно указано.

**Почему natural-language запрос занимает десятки секунд?** CPU inference, объём контекста и переключение трёх локальных моделей при max_loaded_models=1, чтение весов с /mnt/c. Retrieval сам по себе намного быстрее. Мы не утверждаем, что small/strong routing на этой машине обязательно ускоряет полный запрос. Для продукта нужны native Linux storage, кеширование/другой deployment и отдельная проверка SLO.
